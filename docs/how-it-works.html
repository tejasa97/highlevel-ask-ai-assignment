The short version

The LLM plans, our code executes

An LLM can't run code or touch a database. It can only read text and write text. So we describe our actions to it and it writes back which actions to run, with which arguments. Everything else is ordinary backend work: searching, validating, executing, recording what happened. The amber box is the only one that costs money and most of the time.

code · ~20 ms1 RetrieveSearch the 500 action descriptions; keep the ~15 that fit the message.
LLM · ~1 s2 PlanModel sees message + 15 actions, writes a JSON plan of steps.
code3 ValidateCheck args against schemas, turn names into IDs, decide what needs confirming.
code4 ExecuteRun steps (in parallel where possible), stream progress to the chat.
code5 SummarizeBuild the reply from real results: done, failed, pending.
Five ideas you need

The new vocabulary, in backend terms

Idea 1

Tokens: the unit of cost and latency

Models don't read characters or words. They read tokens, chunks of roughly 3–4 characters of English. Every request is billed per token: input tokens (everything you send) and output tokens (everything the model writes).

Create a contact named Sarah with sarah@acme.io

≈ 11 tokens. The exact split depends on each model's tokenizer; this one is illustrative.

  • Input drives cost. Every call resends the whole prompt: instructions, tool descriptions, conversation. 500 tool descriptions at ~120 tokens each is ~60,000 tokens per call.
  • Output drives latency. The model writes one token at a time, so a 400-token plan takes noticeably longer than a 40-token answer. Keep outputs short and structured.
  • Context window is the max tokens per call. A prompt that's too big doesn't fit, and a prompt that merely fits still gets worse at picking the right tool.
  • Prompt caching: if the start of your prompt is byte-identical to a recent call, the provider reuses it, which is cheaper and faster. So put the stable parts first and the changing parts last:
system + plan rules (cached)
15 tool cards
context
msg

Backend analogy: tokens are like bytes on a metered API, and prompt caching is a CDN for the prefix of your request.

Idea 2

Embeddings: search by meaning

An embedding model turns text into a vector, a list of a few hundred numbers. Texts that mean similar things land close together, even with no words in common. “Add Sarah as a new person” lands near “Create contact” although it never says “contact”.

We embed every action once, at startup, and store the vectors. Per message we embed only the message (free and a few milliseconds with a local model) and take the nearest actions by cosine similarity. That is the Retrieve stage.

Real vectors have 384 to 3,000+ dimensions; this is a hand-drawn 2-D picture of the idea. Scores here are illustrative.

  • We embed example requests, not descriptions. Each action gets ~5 phrasings a user might type, e.g. “who hasn't got back to us” and “leads gone quiet” for List unanswered conversations. A message is compared with phrasings that look like messages, and an action scores by its best match, so one action can be reached by very different wordings. They never reuse the brief's or the evals' prompts.
  • Short follow-ups borrow context. “Make those due tomorrow” has almost nothing to search on, so before embedding we add what the conversation is about (“tasks, leads”) to the query.
  • Long requests are split. A four-part request becomes four clauses, each retrieved on its own, so the longest clause doesn't drown the others in one averaged vector.
  • What embeddings can't see: direction and negation. “Haven't replied” sits right next to “unanswered”, though one means we wrote last and the other means the customer did. That's fixed in the action's wording and parameters (waitingOn), not in search.

Backend analogy: a vector index is a nearest-neighbour lookup instead of a B-tree lookup. With only 500 rows, a plain loop over an in-memory array is fast enough; no vector database needed.

Idea 3

Keyword search covers what embeddings blur

Embeddings are fuzzy, and they can rank “Set product SKU” below “Update product details” for “set the SKU on the blue mug”. Classic keyword search (BM25, the algorithm behind Elasticsearch scoring) nails exact terms like SKU, invoice, no-show. We run both and merge the rankings (hybrid retrieval), then keep a few actions from each relevant module so look-alikes from different modules all reach the model.

We measure this stage on its own as recall@15: for each eval scenario, did the right actions make the shortlist? If retrieval misses, the model can't pick the right action, however smart it is.

Backend analogy: the same trick as combining a full-text index with a semantic re-ranker in product search.

Idea 4

Tool calling: the model asks, your code acts

With tool calling (also called function calling), you send the model a list of tools, each a name, description and JSON Schema for its arguments. Instead of plain text, the model can reply “call create_contact with these arguments”. Your code runs it, sends the result back, and the model continues. Here is one full round trip:

① Your server → model

Instructions, tool definitions, the user's message.

{
  "system": "You are Ask AI for a CRM...",
  "tools": [{
    "name": "create_contact",
    "description": "Create a new contact person...",
    "input_schema": {
      "type": "object",
      "properties": {
        "firstName": { "type": "string" },
        "email":     { "type": "string" }
      },
      "required": ["firstName"]
    }
  }],
  "messages": [{ "role": "user",
    "content": "Create a contact named Sarah, sarah@acme.io" }]
}

② Model → your server

No prose. A structured request to call a tool, with arguments it extracted from the sentence.

{
  "stop_reason": "tool_use",
  "content": [{
    "type": "tool_use",
    "id": "tu_01",
    "name": "create_contact",
    "input": {
      "firstName": "Sarah",
      "email": "sarah@acme.io"
    }
  }]
}

③ Your code runs the handler

Validate input with Zod, call the handler, write to SQLite. The model is not involved.

{
  "id": "ct_0142",
  "firstName": "Sarah",
  "email": "sarah@acme.io",
  "createdAt": "2026-10-20T14:02:11Z"
}

④ Server → model again → final text

Resend the whole conversation plus the result. The model then writes the reply, or asks for another tool.

{ "role": "user", "content": [{
    "type": "tool_result",
    "tool_use_id": "tu_01",
    "content": "{\"id\":\"ct_0142\"}"
}]}
→ "Created Sarah (ct_0142)."

Field names follow Anthropic's Messages API; OpenAI and others use the same idea with slightly different names.

Multi-turn tool calling means repeating ②→③→④ until the model stops asking for tools. That repetition is where cost goes: each round trip resends everything so far, including every tool result. A task that touches 6 leads, one tool at a time, can easily take 15+ calls.

Backend analogy: the model is a client that can only send RPC requests. It never gets database access; your server decides what to run, so authorization stays in code.

Idea 5

Our twist: no tools, one submit_plan reply

Instead of handing the model 15 tools and looping, we give it no tools. Its reply must match one JSON Schema, submit_plan, using the provider's structured-output mode. That schema is our plan grammar. (We first planned to force a single tool call, but Claude Sonnet 5.5 and Opus 5.5 reject forced tool choice with an error, and structured output works on Anthropic and OpenAI alike.) The 15 retrieved actions go in the prompt as cards it can reference. So the model writes the whole program in one go:

{
  "type": "plan",
  "steps": [
    { "id": "s1", "action": "M03.A03", "args": { "createdAfter": "2026-10-12" } },
    { "id": "s2", "action": "M11.A10", "args": { "waitingOn": "contact" } },
    { "id": "s3", "op": "filter", "in": "$s1.items",
      "where": { "contactId": { "in": "$s2.items[*].contactId" } } },
    { "id": "s4", "op": "forEach", "in": "$s3",
      "do": [{ "action": "M06.A01", "args": { "title": "Follow up with {{$item.name}}" } }] }
  ]
}
  • References, not data. $s1.items means “whatever step 1 returns”. The model never sees or retypes the 14 lead records, so it can't invent one, and they don't cost tokens.
  • Built-in ops (filter, exclude, forEach, if) run in our executor. Looping over 200 leads is a for loop in code, not 200 model calls.
  • Other answers the tool allows: clarify (ask one question), unsupported (say no honestly), search_tools (“I need a different shortlist”), and an observe step (“show me this result before I decide the rest”).
  • The reply is built by code from execution results, so a direct request needs one LLM call, not two.

Backend analogy: the model is a query planner that emits a plan tree, and our executor is the database engine that runs it.

Reference

Glossary

Token
The unit models read, write and bill by; about ¾ of an English word.
Context window
Maximum tokens in one call, input and output together.
Embedding
A vector representing a text's meaning. Similar meaning, nearby vectors.
Cosine similarity
How we compare two embeddings: 1 means same direction, 0 means unrelated.
BM25
Classic keyword relevance scoring. Good at exact terms, blind to synonyms.
Tool / function calling
The model replies with a structured request to call a named function with JSON arguments; your code runs it.
ReAct loop
Reason → act (call one tool) → observe the result → repeat. Simple, but one model call per step.
Structured output
Making the reply match a JSON Schema, here the submit_plan schema (Anthropic output_config.format, OpenAI text.format).
Temperature
Randomness of the model's choices. We use 0 for planning and evals, so runs repeat as closely as possible.
Hallucination
The model stating something untrue with confidence. We contain it by never letting the model report results; code does.
TTFUR
Time to first useful response: the plan checklist, a result, or a question. A spinner doesn't count.
p50 / p95
Median and 95th-percentile latency over all eval runs.

# Grounded planner outcomes

Implemented on `codex/planner-record-lookups`, after the record-lookup batch (`f0870a6`). Shared by every provider: no model-name branching, embedding-model replacement or second executor.

## Seven changes

1. **Lookup before identity questions.** `clarify` carries a typed `clarification` category and, for identity, a `lookup` selector. The app validates qualifiers and queries the existing resolver before returning the question. Real duplicates produce options derived from actual records; more than eight matches require a narrower name/qualifier. A unique, missing or inactive match gets one grounded replan. A repeated question about the same unique match fails safely. Lookup itself never mutates records or bypasses inactive-user checks.
2. **Explicit final outcome.** Every new wire reply declares `outcome: { effect, actions, destination }`. `actions` identifies final requested operations, not prerequisite searches. The first declaration is retained across search/look/repair; an initially empty action list can be filled after discovery. A change cannot finish with reads alone or a prose answer; missing declared operations go through the existing single repair budget. A read request cannot introduce writes. Plans still compile against only offered actions and execute through existing permissions/confirmation. This checks the model's declared interpretation, not semantic equivalence with the user's words, per-record completeness, or successful final domain state. It is not an independent task verifier. Historical saved replies remain parseable without the new fields.
3. **Retrieval metadata.** Module-owned general synonyms are merged with generated synonyms for both lexical and dense retrieval. Assignment describes workload handoff; membership describes joining an existing team rather than creating one or changing its manager. Refund requests declare their payment dependency. Task creation declares optional relationships separately; those do not become mandatory through generated metadata fallback. Optional dependency expansion is considered only for a matching typed mention. No wholesale sibling expansion or scenario sentence copies.
4. **Weekday dates.** `<now>` supplies seven precomputed `upcoming`/`next` dates using the account's `America/New_York` date. Bare weekdays include today; an explicit “next Friday” is strictly future. Weekend rollover and DST are tested. This is a documented product convention, not a claim that English has only one interpretation. Conflicting dates and genuinely unspecified required times still require clarification.
5. **Invoice reminder eligibility.** `M28.A10.notRemindedSince` is an optional ISO calendar date. It excludes invoices whose latest reminder is on/after local midnight on that date, retains older/null reminders, and filters before pagination. “Skip reminded this week” uses Monday from `<now>`. It is read-only; delivery consent, the 24-hour limit, billing permission and executor approvals remain unchanged.
6. **Draft wording, not facts.** The shared instructions allow ordinary message composition from a supplied purpose. They still prohibit invented addresses, amounts, offers, attachments or commitments. Exact prose is requested only when necessary or requested by the user. This is prompting guidance, not a deterministic fact checker; domain delivery rules and approval remain the backstop.
7. **Delivery capabilities before content questions.** Module actions declare a `destination` surface. The registry publishes the supported IDs, labels and action IDs in `<delivery_surfaces>`. The planner must preserve an unsupported platform instead of substituting a similar blog/community action. The app rejects an unlisted declared destination before asking content questions or running reads, and checks declared destinations against annotated actions. Public publishing, business listings/reviews, email and SMS have explicit surfaces. This is not a platform keyword blacklist or a substitute for domain permissions. Simulated directory publication remains simulated; metadata does not add real integrations.

## Additional interface correction

A query that only persists internal bookkeeping can declare `query: true` (report execution and trigger condition testing). It may satisfy a read outcome even though its existing execution risk is `write`. Trigger testing records only a test firing and never starts a workflow. This does not change confirmation, permission or handler behavior. Registry validation forbids marking external/destructive actions as queries. The broader development runs caught and motivated these corrections: the initial quality guard incorrectly rejected them. The other simulated response/payment/message actions create domain records or change consent and are not bookkeeping-only queries. Report discovery also explicitly directs metric/ranking questions to actual computation rather than stopping at saved definitions.

Round-robin references use the actual list item schema: a User has `$rr.id`; some team summaries have `$rr.userId`. The old prompt's universal `$rr.userId` example was incorrect. `item` and `rr` are reserved bindings, not step IDs.

## Boundaries and verification

At most one extra identity-check replan, one tool search, one read/replan and one repair are allowed per turn (five planner calls maximum). No retry loop automatically sends or writes. Genuine business choices remain with the user. No automatic team-removal schedule is invented from “for a while”.

Seed data, scenario assertions, frozen reporting data and retrieval questions are unchanged. Regression/development runs are reported separately; already inspected scenarios are not a new holdout. Initial development evidence is preserved even when a later source checkpoint improves. See the accompanying validation report for measured results and remaining failures.
